## What this is

Automated weekly social media pipeline for **Love Productions** (loveproductions.com), a New York booking agency (est. 1985, 180+ acts, 70+ countries). The engine turns news about tribute acts and their original artists into platform-native LinkedIn/Instagram/Facebook draft posts, queued in Buffer for human review before publishing.

## Pipeline (end to end)

```
Airtable calendar (appXLETHThc0p5MOz) → upcoming FE shows (next 7 days)
  → Tour dates sheet (TOUR_DATES_SHEET_ID) → ticket URL lookup
  → Google Sheets dedup → Claude Sonnet show announcement posts → Buffer drafts

Airtable artists (appMMwX47V1g2Sv5u, priority-ordered)
  → Claude Haiku web search (news per artist) + whitelisted music-news RSS feeds (lp/feeds.py)
  → Google Sheets dedup → Claude Sonnet content generation → Buffer drafts
  [Phase 4] → remaining slots → Airtable contracts re-bookings (act booked twice by one venue) → Buffer drafts
  [Phase 5] → remaining slots → Claude Haiku testimonial search (source-verified) → Buffer drafts
  [Phase 6] → remaining slots → act spotlights scraped from each act's LP page → Buffer drafts
  [Phase 7] → remaining slots → agency credibility post (LinkedIn only) → Buffer draft
  [Phase 8] → remaining slots → Claude Haiku trivia search (original artists) → Claude Sonnet posts → Buffer drafts
  [Phase 9] → still-remaining slots → Claude Haiku historical fact search → Claude Sonnet posts → Buffer drafts

Buffer analytics → top performers → injected as style examples into every generate_posts() call

Every topic queued to Buffer (shows, artist news, trivia, historical facts)
  → Claude Sonnet long-form article (generate_article) → LP News WordPress plugin → draft post on loveproductions.com
```

Show announcements and artist news compete for slots first (Phases 1-3), then the buyer-proof fills (re-bookings, testimonials, act spotlights, agency credibility, Phases 4-7), then the Instagram/Facebook filler (trivia and historical facts, Phases 8-9). All phases feed the same dedup store and Buffer queue. **Every** topic that gets queued to Buffer also gets a dedicated long-form article drafted as a standard WordPress post on loveproductions.com (see "Website news posts" below).

## Important decisions and conventions

**Skill graph as system prompt.** All 13 markdown files in `content-skill-graph/` are concatenated and passed as the system prompt to every `generate_posts()` call. Editing any `.md` file there immediately affects generation, no code change needed.

**Skill-graph rewrite (2026-07-31).** After the client rejected a post as "so AI" (see "IN PROGRESS" below), the graph was reworked rather than patched. What changed:
- **New file `voice/reference-posts.md`, and it is the most important file in the graph.** It holds the rejected post verbatim with a six-point diagnosis of why it failed, a rewritten version, and the Reliant Talent Agency post the client asked us to imitate (17 words over a 7-slide carousel). Rules describe; worked examples calibrate. `index.md`, `humanizer.md` and `linkedin.md` all point at it.
- **LinkedIn length dropped from 500-700 characters to 200-300 characters of copy** (the booking link does not count toward the budget), hard ceiling 400, two or three sentences. Changed in `linkedin.md`, `platform-tone.md`, `repurpose.md` and the `generate_posts()` prompt together, so nothing contradicts.
- **The LinkedIn CTA is now Steve's calendar link, not the info@ email** (client direction). `generate_posts()` injects `config.STEVE_CALENDAR_LINK` via `booking_cta_instruction`, since the model cannot use a URL it was never given; the graph only describes the rule. Falls back to the email when the env var is unset.
- **`index.md` rewritten.** It was badly stale (still advertised LinkedIn at 1,300-2,000 characters and claimed shows bypass scoring). It now opens with three override rules: short, one hard fact up front, and the graphic carries the message.
- **`humanizer.md` gained a "Length is the loudest tell" section** placed above every other pattern, plus entries for "the kind of X that Y" and claims dressed as evidence, with the rejected post's two symmetrical constructions quoted as the worked example.
- **`buyers.md` gained a "How NOT to talk to them" section** (they work in live entertainment; do not explain the business to them) and its content list now matches what the engine actually produces, with post-show recaps explicitly marked as deliberately not produced.
- **Verified by real generation, not by inspection.** Two topics run end to end: an act spotlight came back at 296 characters and a re-booking at 301 (156 of copy), both leading with the hard fact, both zero em dashes, both using the calendar CTA.

**Earlier length work (client direction 2026-07-24), superseded above.** The client found output too long and too AI-sounding. Two levers: (1) length (the figures in this paragraph are historical, see the rewrite above for current targets), and `generate_article()` writes 2 to 3 short paragraphs. `generate_posts()` and `generate_article()` both carry explicit length + "sound human" instructions in `lp/ai.py` on top of the skill-graph rules. (2) anti-AI, `humanizer.md` was expanded: more banned AI words, plus rules against the rule-of-three, symmetrical "not just X but Y" sentences, teaser scaffolding, rhetorical-question openers, uniform sentence length, and adjective-over-specifics writing. **Real brand voice** now lives in `brand-voice.md` under "Real Brand Voice (from loveproductions.com)", verbatim copy pulled from their About page, act pages, and a news article (credentials-first, specific venues/awards/years, warm). There's an HTML-comment placeholder there to paste more client-approved examples; the more real examples, the closer generation stays to their voice.

**Two models.** Haiku (`SEARCH_MODEL`) for news search and anything cheap/mechanical. Sonnet (`CONTENT_MODEL`) for content generation. Never swap them without considering cost impact.

**API refusals abort the run's Claude work (2026-07-31).** Every search helper catches its exception and returns `[]`, which is indistinguishable from "nothing found". When a real run hit the account usage limit, it walked the entire roster logging "No trivia found" for each act and reported success with **0 topics**, which would have been a silently empty week. `config.record_api_exception()` now flags account-level refusals (matched on "usage limit", "credit balance", "quota", "billing", since Anthropic returns these as **400 invalid_request_error**, not 429) and sets `config.api_blocked`. `under_cost_cap()` returns False while that is set, and since every Claude call is already gated on it, one check short-circuits the whole run. Transient failures (timeouts, bad JSON) deliberately do **not** set it.

**Cost cap.** Default $5/run (`COST_CAP_USD`). Each full topic costs ~$0.06 (1 search + 1 generate). Cap is checked before every Claude call via `config.under_cost_cap()`. Mutable cost state lives in `lp/config.py` (`estimated_cost_usd`, `claude_call_count`) and is mutated directly from `lp/ai.py`.

**Buffer rate limits.** Two distinct limits:
- *Per-minute:* 60 requests/minute. Both `main.py` and `clean_up.py` read `retryAfter` from 429 responses and retry. If no `retryAfter`, defaults to 61s wait.
- *Daily:* Hard 24h cap per API client (`"window":"24h"` in the 429 body). When hit, `clean_up.py` exits immediately with a clear message. Nothing to do but wait until the next day. Running `main.py` followed immediately by `clean_up.py` is enough to exhaust the daily limit, so space them out.
- Both scripts use the GraphQL API at `https://api.buffer.com`. The legacy REST API (`api.bufferapp.com`) does **not** accept OIDC tokens, don't use it.

**Buffer GraphQL notes.** Fetching posts requires `organizationId` (not `channelId`) in `PostsInput`. Updating posts uses `editPost` mutation (not `updatePost`). **Deleting posts:** `deletePost` returns the union `DeletePostPayload` whose members are `DeletePostSuccess { id }` and `VoidMutationError { message }`, **not** the `PostActionSuccess`/`MutationError` union used by create/edit. Spreading the wrong fragments causes a silent GraphQL 400 (`_buffer_gql` then returns `{}`); the delete helpers now treat success as `"id" in result` so an empty/errored response is logged as a failure, not a false "Deleted". Both delete paths (`purge_expired_show_drafts()` in `lp/buffer.py` and `_delete_post()` in `clean_up.py`) use this corrected shape. Facebook edits require `metadata.facebook.type`. Instagram edits require `metadata.instagram.type` + at least one image (use the LP logo placeholder). **Note:** Buffer removed `status` and `after` (pagination cursor) from `PostsInput` in a 2026 API update. `get_occupied_slots()` now fetches a single page only (no pagination), sufficient for checking this week's 7 slots. `fetch_top_performers()` uses a `statistics` field that may or may not be available; it degrades gracefully to `[]` if not.

**No em dashes (client rule).** Em dashes are banned everywhere: social posts, website articles, and the docs/code in this repo. The skill graph enforces **zero em dashes per post** (see `humanizer.md`), and `generate_article()` repeats the rule. Use a comma, a colon, a semicolon (sparingly), or a full stop and a new sentence instead. En dashes ("–") are out too. The `replace(" — ", "—")` normalization still runs in `main.py` as a spacing safety net for any stray dash that slips through, but the goal is that none appear in the first place.

**Show announcements (calendar pipeline).** `fetch_upcoming_shows()` pulls from Airtable base `appXLETHThc0p5MOz` (env: `AIRTABLE_CALENDAR_BASE_ID`), table `tblK2LMog1WUEv3j0`. Filters for `LPC Contract Status = "(FE) Fully Executed"` and show dates within the next 7 days (`SHOW_DAYS_AHEAD`). Dedup key is `lpc_{LPC #}` stored in the url column of Sheets. Test with `python main.py --test-calendar`. **As of the interleave change (2026-07-13), show announcements no longer bypass scoring or claim slots first**, see "Scoring and scheduling" below. Each upcoming show is collected as a candidate (ticket/venue enrichment happens at collection time, flagged `_is_show=True`, carries `_show` for `mark_show_used()`), given a baseline `_score = config.SHOW_BASE_SCORE + exclusivity_bonus(...)`, and competes head-to-head with news in one ranked pool. Consequence: when shows + news exceed the 7 weekly slots, the lowest-scoring items, **shows included**, are dropped and not announced.

**Artist names are exact.** The `artists.md` table maps tribute act names exactly as they appear in Airtable. Claude searches for the exact name, do not paraphrase. "Concert of Kings" (not "Elvis: The Concert of Kings"). Priscilla Presley is a separate act from Concert of Kings. **Note:** Airtable still has the old name "Elvis: The Concert of Kings", needs to be updated there too for the mapping to work correctly.

**Expired draft cleanup.** `purge_expired_show_drafts()` lives in `lp/buffer.py` but is **commented out** at the top of `main()` in `main.py`. It detects show announcement drafts with past dates and deletes them. Uncomment when ready, always test with `--dry-run` first. The same logic is active (not commented out) in `clean_up.py --purge-expired`.

**Dry run output.** `main.py --dry-run` prints full post text (not truncated) with scheduled slot per post. Safe to run to preview output without writing to Sheets or Buffer.

**Scoring and scheduling (shows + news interleaved by score).** As of 2026-07-13, shows and news compete for the same 7 weekly slots in **one ranked pool**, shows no longer claim the earliest slots up-front (this fixed the bug where a full week of Airtable shows left artist news with zero slots). `main.py` runs these phases:
1. **Collect show candidates**, each upcoming Airtable show → topic, ticket/venue enrichment, `_is_show=True`, `_score = config.SHOW_BASE_SCORE + exclusivity_bonus(priority, act)`. No generation/posting yet. (Skipped in news-only mode.)
2. **Collect news candidates**, search all artists (web search + RSS feeds), dedup vs. `used`.
3. **Score news** in one Haiku call (`score_and_rank_topics()` in `lp/ai.py`): five criteria (relevance, freshness, velocity, virality, uniqueness) + an exclusivity +1.0 bonus via `exclusivity_bonus()` (Top of Roster / Exclusive, plus hardcoded Tony Danza & The Rocket Man Show). Below-0.40 dropped.
4. **Re-score gig-date news**, any news item the search tagged `hook_type == "upcoming_show"` (a tribute-act live date) is a show announcement, not news, so its score is overwritten with `config.SHOW_BASE_SCORE + exclusivity_bonus(...)`, the same baseline as an Airtable show. This stops exclusivity-boosted gig dates from crowding genuine news (releases, awards, original-artist news) out of every slot. (No-op in news-only mode, where `upcoming_show` items are dropped from the pool entirely.)
5. **Merge, sort, select**, `pool = show_candidates + ranked_news`, sorted by `_score` desc, then `_select_with_diversity(pool, len(week_slots))` (no act more than twice consecutively). When shows + news > slots, the lowest-scoring items (shows *or* news) are dropped.
6. **Generate + post** each selected topic in one unified loop (branch on `_is_show` only for dedup bookkeeping: shows → `mark_show_used()`; news → `mark_topics_used()`). Platforms come from `hook_type` (upcoming_show/tribute_news → all 3; original_artist_news/trivia/historical_fact → IG+FB). `_build_news_post()` returns `None` for `upcoming_show`, so shows and gig dates get no website article.
7. **Fill leftover slots**, in this order: re-bookings, testimonials, act spotlights, agency credibility (Phases 4-7, see "LinkedIn supply" below), then original-artist trivia (`search_trivia()`), then pre-1990 historical facts (`search_historical_facts()`). Driven by `_fill_with_facts()` / `_fill_with_topics()` through the local `_run_phase()` closure, only slots the ranked pool didn't fill, only acts not already scheduled, skipped in `--artist` single-artist mode.

`SHOW_BASE_SCORE` (default 0.75, env-overridable) is the knob that decides how strong a news story must be to outrank a routine show/gig-date: it sits in the normal news-score range so shows and news compete on an **even playing field** (per client direction 2026-07-13). Raise it to protect shows, lower it to favor news. `get_week_slots()` always returns exactly 7 slots (next 7 days at 10am ET). `post_draft_to_buffer()` accepts an optional `scheduled_at: datetime`, when set, uses `schedulingType: "scheduled"` + a Unix timestamp; otherwise queue mode. If the week has no open slots, everything (shows included) is skipped.

**News-only mode (`--news-count N`).** A standalone run mode for filling Buffer with news on demand, independent of the weekly calendar. Sets `news_count` on `main()`, which: (1) **skips show announcements** entirely, both the Airtable calendar show loop (iterates an empty list) *and* tribute-act live-date items surfaced by the news search: candidates with `hook_type == "upcoming_show"` are dropped from the pool before scoring/selection (the same items the website step already skips via `_build_news_post`), so freed slots backfill with real news/trivia/historical and the run still targets N. (Normal weekly runs keep `upcoming_show` news items to promote gigs, the drop is news-only-mode only.) (2) replaces the week-slot list with `[None] * N`, a `None` slot flows through the whole pipeline as "queue this draft" (`post_draft_to_buffer(scheduled_at=None)` → Buffer queue mode, no fixed time), ignoring which slots are already occupied, (3) targets **up to N** posts: artist news first (Phase 3, capped at N via `_select_with_diversity(ranked, N)`), then tops up any shortfall with the fill phases (re-bookings, testimonials, spotlights, agency, trivia, historical facts) to reach N. Fewer than N real news stories → fewer real-news posts, filled to N by the rest. All the slot-formatting log lines guard for `None` ("queue"/"queued"), and `_fill_with_facts()` uses today (ET) as the search-date context when the slot is `None` (needed because `search_historical_facts()` requires a real date). Website news posts, dedup, and cost caps behave exactly as in a normal run. Combine with `--dry-run` to preview.

**Music-news RSS feeds (second news channel).** `lp/feeds.py` reads a curated whitelist of music-outlet RSS feeds (`MUSIC_FEEDS`) as a second candidate-topic source *alongside* Anthropic's hosted `web_search` (used by `search_artist_news()`). RSS is the publisher-sanctioned syndication channel: we read headline + summary + the outlet's own article link, never article bodies. In Phase 1 of `main()`, `load_feed_items()` fetches all feeds **once** (stdlib `xml.etree` + `requests`, no new dependency, never raises, in-process cache, items filtered to the last `FEED_DAYS`=14 days). For each artist, `search_artist_feeds(name, original, feed_items)` returns items whose title/summary mention the tribute act (→ `tribute_news`) or an original artist (→ `original_artist_news`), in the exact dict shape `search_artist_news()` returns, so they flow through the same score → dedup → generate → Buffer path. Feed + web-search results are deduped by url/headline within each artist's batch before `filter_new_topics()`. The **original-artist live-event hard rule** is enforced here too: any `original_artist_news` item matching `_LIVE_EVENT_RE` is dropped. Name matching uses word boundaries and a 4-char minimum to avoid ambiguous short-name collisions; original-artist cells with multiple names are split on `,`/`&`/`/`/`and`. **Whitelist (as of 2026-07-03):** Billboard, Pitchfork (`/feed/feed-news/rss`), Rolling Stone, Stereogum, Brooklyn Vegan, American Songwriter, NME. Pitchfork's feed works from our own server via `requests` (Condé Nast only IP-blocks Anthropic's WebFetch/web_search infra, not us). **Deliberately excluded:** Consequence (robots.txt disallows `/feed/` and blocks ClaudeBot). To add/remove an outlet, edit `MUSIC_FEEDS` in `lp/feeds.py`, verify the feed's robots.txt permits it first. Note tribute-name/original-artist nickname collisions (e.g. "The Fab Four" the act vs. "Fab Four" the Beatles nickname) can classify an item as `tribute_news`; harmless (still relevant, routes to all platforms).

**Always name the tribute act (both channels).** Per client direction (2026-07-16), every social post and every website article must mention the tribute act by name, even when the story is about the original artist (original_artist_news / trivia / historical_fact), tie the story back to the LP act. `generate_posts()` and `generate_article()` both resolve the tribute act as `topic["_act"]` (falling back to `topic["artist"]`, because for original-artist news the `artist` field can be the *original* artist's name, not the tribute act) and set that as the "Tribute Act:" prompt line. On the **website article only**: every article ends with a booking CTA phrased `"If you're interested in booking <act>, please follow this link to set up an appointment with Steve Love."` where **"this link"** (not Steve's name, client preference 2026-07-16) is an inline HTML anchor to `config.STEVE_CALENDAR_LINK` (env `STEVE_CALENDAR_LINK`; `.env` also has a `BEN_CALENDAR_LINK`, currently unused) and "Steve Love" stays plain text. The tribute act's name is mentioned in the body as **plain text, no hyperlink** (client direction 2026-07-16: the "Read more" button already links out, and the reader is already on loveproductions.com, so an inline act-page link is redundant). The "this link" CTA anchor is the **only** link allowed in the article body, no other links/raw URLs; the "Read more" button still carries the source link. (`generate_article()` no longer takes `artist_url`; `_build_news_post` still uses `artist_url` for the button-URL fallback via `_news_button_url`.) The plugin's `wp_kses_post`/paragraph pipeline preserves the `<a>` tags (no plugin change needed). Social posts can't hyperlink a name, so they just name the act in the copy. In the Buffer→website backfill (`_buffer_posts_to_news`), `_match_artist()` (renamed from `_match_artist_url`, now returns the matched Airtable artist dict) sets `topic["_act"]` so backfilled articles also get the tie-in + booking CTA + linked name. If `artist_url` is empty the act name stays plain text; if `STEVE_CALENDAR_LINK` is unset the CTA still appears with "this link" as plain text.

**Artist page URLs (`lp/artist_links.py`).** Every act's loveproductions.com page lives under the site's `/title-item/` directory. The primary source of `artist_url` is the Airtable scan (`_artist_url_from_fields`), but to guarantee the tribute-act anchor above never blanks at runtime, `lp/artist_links.py` holds a prepopulated `ARTIST_PAGE_URLS` map (act name → title-item URL) covering the full current roster (all 24 acts, each verified HTTP 200 on 2026-07-16). `fetch_airtable_artists()` now falls back to `lookup_artist_url(name)` (case-insensitive, whitespace-tolerant) when the Airtable row has no link. Airtable's own value always wins; only add an entry to the static map when a new act's Airtable link is or might be missing.

**Platform routing by hook type.** All routing lives in **one** function, `_platforms_for(hook_type)` in `main.py`, used by both the ranked-pool loop and every fill phase. Three cases:
- **LinkedIn only:** `agency_proof`. An agency-level post is not about any one act, so it has no place on the fan channels.
- **Instagram + Facebook only:** `original_artist_news`, `trivia`, `historical_fact`, `upcoming_show`.
- **All three:** everything else, i.e. `tribute_news`, `rebooking`, `testimonial`, `act_spotlight`.

`hook_type` is set by Claude during search (`search_artist_news()`), or hardcoded by the source that builds the topic (`search_trivia()`, `search_historical_facts()`, `search_testimonials()`, `build_act_spotlight_topic()`, `build_agency_topic()`, `fetch_rebookings()`). **LinkedIn is a proof/credibility channel, not a show flyer** (client direction 2026-07-24): the client found a long show-announcement LinkedIn post too long and too AI-sounding, so show/date announcements (`upcoming_show`) no longer post to LinkedIn at all. `generate_posts()` still returns a `linkedin` key for every topic; `_platforms_for()` decides which platforms actually receive it, and the unused drafts are discarded.

**Reserved LinkedIn slots (`LINKEDIN_RESERVED_SLOTS`, default 2).** The four types above only fill slots the ranked pool leaves open, and in a busy week the pool takes all 7. **Dedup keys: `sheet_key` wins.** `topic_key(item)` in `lp/ai.py` is now the single definition of a topic's dedup key: explicit `sheet_key`, then `url`, then `headline`. `filter_new_topics()` and `mark_topics_used()` both use it, and `mark_topics_used()` writes that key into the Sheets **url column** (matching what `mark_show_used()` already did with `lpc_{LPC #}`). **Slot-filling helpers in `main.py`.** `_draft_topic()` holds the per-topic work (generate, route via `_platforms_for()`, draft to Buffer, build the website article) and is shared by every fill phase. Two drivers sit on top: `_fill_with_facts()` for per-act searches (`search_fn(act, original, slot_date)`, with `require_original` to gate on an original-artist mapping and `max_items` to cap the phase) and `_fill_with_topics()` for ready-made topics that need no search (re-bookings, agency). In `main()`, the local `_run_phase()` closure runs each phase and consumes only the slots it actually used, so phases chain without manual slot arithmetic.

**Per-platform link/image handling (og:image scraping).** `fetch_og_image()` in `lp/scrape.py` scrapes a topic's source URL for its Open Graph preview image (og:image → og:image:url → twitter:image fallback), resolving relative URLs and returning `None` on any failure. It's cheap, one `requests.get()` with a 5s timeout + regex, **no AI call**, in-run cache by URL, no new dependency. Called once per topic in all three posting blocks of `main.py`; `_image_for(platform, og_image)` then routes the result:
- **LinkedIn**, image-only post, **no link card**. Gets the scraped image as a native asset; if none is found, posts text-only. The source URL is deliberately **omitted** from the LinkedIn body (see `generate_posts()` instruction) so LinkedIn can never render a link-preview card. This is what the client wants.
- **Instagram**, uses the scraped image, falling back to the LP logo placeholder (`config._IG_PLACEHOLDER`) when none is found.
- **Facebook**, gets **no** image asset; the source URL stays in the body so Facebook auto-unfurls its own native link-preview card (with the og:image). `generate_posts()` now weaves the source URL into the **Facebook post only** (previously LinkedIn + Facebook).

`post_draft_to_buffer()` attaches `assets.image.url` for both Instagram and LinkedIn (Facebook never gets an asset). **Unverified:** that Buffer's GraphQL accepts `assets` for LinkedIn channels, confirm with one live (non-dry-run) post; if rejected, the LinkedIn asset/metadata shape may need adjustment (e.g. a `metadata.linkedin` field).

**Trivia.** After the artist news pipeline and the buyer-proof phases fill their slots, the next remaining week slots are filled by `search_trivia()`, surprising, lesser-known facts about the **original artist**, any era, not date-bound (distinct from historical facts, which are pre-1990 archival and date-anchored). Sits just below original-artist news in the hierarchy and **above** historical facts. Instagram + Facebook only (`hook_type = "trivia"`), generated only for artists with an original artist mapping that weren't already scheduled this run, and excluded in `--artist` single-artist mode. Deduped via the same Sheets mechanism as news topics. Hook guidance lives in `content-skill-graph/engine/hooks.md` ("Trivia about Artist Represented by Tribute").

**Historical facts (last phase).** After trivia fills what it can, any still-remaining week slots are filled by `search_historical_facts()`, pre-1990 archival facts about original artists from sources like archive.org, old Rolling Stone, Billboard, etc. These are Instagram + Facebook only, lowest priority, generated only for artists with an original artist mapping, and excluded in `--artist` single-artist mode. Deduped via the same Sheets mechanism as news topics. Shares the `_fill_with_facts()` helper in `main.py` with every other per-act fill phase.

**Original artists' shows are never news (hard rule).** We never announce an original artist's own tour, concert, residency, festival appearance, or any live-performance date and then point to our tribute band, it looks bad. Enforced in two places: (1) `search_artist_news()` instructs the model to never return original-artist live-event news and to set an `is_live_event` boolean per item; (2) a code-level guard in `search_artist_news()` drops any `original_artist_news` item with `is_live_event == True`, regardless of how the model classified `hook_type`. Original-artist *non-live* news (album/release, award, induction, biopic, anniversary, milestone, passing, etc.) is still eligible. The rule and an updated example also live in `content-skill-graph/engine/hooks.md` under "News from Artist Represented by Tribute". Tribute acts' own live dates are unaffected, those are exactly what we promote.

**Ticket links and venue names in show announcements.** `lookup_ticket_url()` in `lp/sheets.py` looks up a ticket URL *and* venue name in the tour dates Google Sheet (`TOUR_DATES_SHEET_ID`) produced by the `lp-tour-dates` repo (formerly `love-automations`; local dir `/Users/jonathankohen/lp-tour-dates`). The sheet has per-artist tabs named by display name (e.g., "Arrival from Sweden" for "Arrival from Sweden: The Music of ABBA") with columns: Date (MM/DD/YY), Venue, City, Region, Country, Ticket URL, Source. The `Venue` field from that table is used to replace the raw address in the headline and summary. If neither source has a venue name, the address is used as-is.

**Website news posts (LP News plugin).** Every topic queued to Buffer is also drafted as a standard WordPress **post** on loveproductions.com.   - **The backfill treated our own links as the source article.** `_first_url()` took the first URL in a Buffer post body, and since 2026-08-03 every generated post carries `STEVE_CALENDAR_LINK` (and act-led LinkedIn posts carry the act page too). So a post with no real source got its "Read more" button pointed at the booking calendar, its featured image scraped from that redirect (which resolved to a **Google account avatar**), and its dedup key set to the calendar URL, meaning the *second* backfilled post carrying that link was silently skipped as a duplicate of the first. Replaced by `_source_url()`, which skips anything on `loveproductions.com`: a source is by definition someone else's page. The act page is still the right **button** fallback and `_news_button_url()` supplies it.
  - **`_build_news_post()` swallowed every article failure.** `generate_article()` returns None on a refusal, a bad parse, **or the cost cap / call limit**, and all of it vanished. A capped run drafts social posts and quietly skips their articles. It now logs a warning naming the hook type, the headline, and the spend so far. **If website posts go missing again, look for that line first.**
- **The backfill and the pipeline can double-publish the same story.** `--news-from-queue` / `--news-from-buffer` key off the source URL or `buffer_<id>`, while the weekly pipeline keys off `sheet_key`, so the plugin's dedup does not see them as the same post. - **Disabled when unconfigured**, if `LP_NEWS_URL`/`LP_NEWS_SECRET` are unset, the website step is skipped (Buffer drafting is unaffected) and the planned posts are logged. `--dry-run` sends `dry_run: true` to the plugin (plans, no writes) when configured.
- **Artist page URLs**, `fetch_airtable_artists()` now requests **all** artist fields (not a fixed subset) and `_artist_url_from_fields()` scans values for a loveproductions.com URL → `artist_url` on each artist dict.   - **Source bitrate below 3.0Mbps** (`_MIN_SOURCE_MBPS`): catches a big frame with no detail in it, e.g. "Highlights from Tony Danza's hit live show" at 1920x1080 and 1.1Mbps. **Only the `source` rendition is measured**; Vimeo's transcodes sit at its own fixed rates and say nothing about the original.
  - **Title** (`_AMATEUR_RE`): "Tony Danza Iphone Clip" is 1080p at 17.8Mbps and passes every numeric test. "N of 269" marks a bulk dump off a camera roll. `_DATED_AD_RE` also gained a numeric-date pattern, since "Vandenberg 'Burning Heart' live 2/27/25 (15) Hartford" is a one-night raw capture (note Vimeo rewrites "/" in titles to a fullwidth solidus).
  - **This requires requesting `width`/`height` from the API**, which the old field list omitted. The renditions cannot stand in for them: Vimeo transcodes a 480p phone clip up to 720 and 1080 renditions, so its download list looks identical to a real promo's.
  - **Fails closed**, like the wrong-act check: no clip beats a bad-looking clip. **20 of 24 acts still have a usable source** and every pick is now a promo, EPK, teaser or 1080p+ production. Two picks changed for the better: Elvis went from a 720p Tupelo audience capture to "3 Elvis Show - 2020" (1080p, 19.8Mbps), Vandenberg from the dated raw live cut to "Judgement Day Live".
- **Still human-gated.** Source selection is heuristic and the quality tests above only rule out what the file gives away, not what a clip looks like. Run `python main.py --test-clips [--artist NAME]` and watch the output before wiring clips into an unattended posting path.

**Em dashes are stripped in code, not asked for in the prompt (2026-07-31).** The rule appears in `humanizer.md`, in `linkedin.md`, and in both `generate_posts()` and `generate_article()`, and the model still produced **seven em dashes across seven posts** in a full dry run. Asking is not enough. `strip_dashes()` in `lp/ai.py` now removes every em and en dash from post copy, article titles and article bodies: a dash before a capitalised word becomes ". " (it was doing a full stop's job, e.g. "Winter Garden, FL—The Rocket Man Show opens..."), everything else becomes ", ". It is the last thing to touch the copy, so nothing downstream can reintroduce one, and it leaves inline HTML alone. **The old `replace(" — ", "—")` in `main.py` was actively harmful**: it normalised the spacing around an em dash while preserving the dash itself, so it made violations harder to spot rather than fixing them. Both call sites now use `strip_dashes()`.

## Deployment: the scheduled run is `origin/main`, and it is easy to forget

`.github/workflows/weekly.yml` runs `python main.py` every Monday at 07:13 UTC on a plain
`actions/checkout@v4` of the default branch. **The client sees whatever is on `origin/main`,
not what is on this machine.**

**This bit us for three weeks (found 2026-08-03).** Nine commits sat unpushed from 2026-07-16
onward, so the July 20, July 27 and August 3 runs all executed pre-`strip_dashes` code. The
drafts came out full of em dashes and five paragraphs long, and it read like the fixes had not
worked rather than like they had never shipped. **Before concluding that a change did not work,
run `git rev-list --left-right --count origin/main...main` and check the commit that the
relevant Actions run actually used.**

**A second, quieter version of the same failure: env vars the code reads but the workflow never
passes.** Every one of these degrades gracefully to "feature off", so nothing errors and the run
reports success. Found unpassed on 2026-08-03 and now wired up: `TOUR_DATES_SHEET_ID` (no ticket
URLs, no venue names, no tour posters), `LP_NEWS_URL` / `LP_NEWS_SECRET` (**no website articles
and no media hosting**, so `upload_media()` returns None and every card, poster and clip is
dropped), `STEVE_CALENDAR_LINK` (CTA silently falls back to info@), `META_PAGE_ACCESS_TOKEN` (no
performance context), `VIMEO_*` (no clips). The workflow also installs `ffmpeg`, which is not in
the runner image and without which clips are skipped silently.

**When adding an env var, add it to the workflow in the same commit.** The tuning knobs
(`SHOW_BASE_SCORE`, `MAX_SHOWS_PER_WEEK`, `VISUAL_MIN_PER_WEEK`, `VISUAL_RESERVED_SLOTS`,
`LINKEDIN_RESERVED_SLOTS`, `REBOOKING_MAX_PER_RUN`, `TOUR_CAROUSEL_MIN_*`, `COST_CAP_USD`,
`CARD_DIR`, `VIDEO_DIR`) are deliberately left out,
since their code defaults are the intended production values.

**The booking link is `https://www.loveproductions.com/go/steve` (client direction 2026-08-03).** Not the 200-character Google Calendar URL it redirects to, which was burning most of a LinkedIn post's character budget. **The `www` is required**: `loveproductions.com/go/steve` returns 404, only `www.loveproductions.com/go/steve` redirects. Set in `.env` **and** as a repo secret; the two had drifted, `.env` already held the short link while the Actions secret still held the long one, which is why the live run used the long form.

**Editing drafts in place: `edit_post_draft()` in `lp/buffer.py`. Read this before using it.**

**An edit that omits `saveToDraft` publishes the post.** On 2026-08-03 an edit meant only to attach an image put three posts live across LinkedIn, Instagram and Facebook, and moved two others from draft to scheduled-to-send. Buffer does not treat a missing `saveToDraft` as "leave it as it was": it takes the edit as a non-draft update, discards the post's custom time, re-slots it into the automatic queue, and for a slot already in the past sends it immediately. `edit_post_draft()` now always sends `saveToDraft: True`.

**An edit that omits `dueAt` discards the post's schedule**, which is how the two survivors ended up due the next morning instead of five days later. Callers editing a scheduled draft must pass `scheduled_at` back in.

**`SchedulingType` has only `automatic` and `notification`** (introspected 2026-08-03). There is no `scheduled` member; the mutation rejects it outright. The time is carried by `ShareMode` (`addToQueue` / `customScheduled` / `shareNext` / `shareNow`) plus `dueAt`, exactly as `post_draft_to_buffer()` does it.

The per-network metadata rules from create apply here too: Facebook and Instagram edits are rejected without `metadata.<network>.type`, and an Instagram edit needs at least one image. **Verify with a `fetch_buffer_posts(statuses=("draft","scheduled","sent"))` check after any bulk edit**; a post that left `draft` will simply vanish from a drafts-only listing, which reads as "nothing happened" rather than as the alarm it is.

**Buffer post-type enums, introspected 2026-08-03 rather than guessed.** Two of these were wrong in code and both failed loudly only at runtime:

- `SchedulingType` is only `automatic` | `notification`; `ShareMode` is `addToQueue` | `customScheduled` | `shareNext` | `shareNow`.

**`post_draft_to_buffer()` used to log "Buffer draft created (id=)" on failure**, because it logged before checking the id. The run log therefore read as a success while the function returned False, which is how two failed Facebook drafts nearly went unnoticed. It now logs an error and returns early.

**The act may never be called "Elvis" anything (client direction 2026-08-12).** The client's words: "we can't use the name Elvis anywhere. So, 'Elvis: Concert of Kings' is a no-go." The act is **The Concert of Kings**. Confirmed with the client the same day: the ban is on the **act name only**, so "Elvis Presley" as the original artist is still allowed (`#ElvisPresley`, trivia, news, article copy). Airtable's name is left alone deliberately (dedup keys, the `artists.md` mapping and the tour-sheet tab match all key on it); only the **printed** form changes:

- `ACT_DISPLAY_OVERRIDES` in `lp/artist_links.py` maps the Airtable name to the printable one, applied inside `display_act()`. `generate_posts()` and `generate_article()` now resolve the act through `display_act()` rather than reading `_act` raw, so the act is renamed in copy, hashtags, cards, posters and clip captions at once. **`display_act()` is the chokepoint for any future rename; add an entry there, not a special case at the call site.**
- `banned_act_name_in()` is the enforcement, matching `\belvis\b` **only when not followed by "Presley"** (hyphens are normalized first so a slug is caught too). Three uses: the `generate_posts()` prompt states the rule, `build_hashtags()` drops an offending tag, and a post-generation guard **blanks any platform post the name survives into**, logging which. A name cannot be scrubbed out of a sentence the way a dash can, so the guard drops rather than mangles.
- **The act-page link is suppressed** because its URL carries the name. `/title-item/elvis-the-concert-of-kings/` is visible text on LinkedIn, so the slug breaks the rule as loudly as the copy would. That act's LinkedIn posts now carry the booking line only. **If the client wants the act link back, the page needs a new slug on loveproductions.com.**
- **The 8/15 re-booking drafts were repaired in place**, not regenerated: new stat cards rendered and hosted, copy rewritten, all three drafts edited via `edit_post_draft()` with `scheduled_at` passed back, still `draft`, still 14:00Z.
- **Unchecked: the website article** for this re-booking on loveproductions.com. The plugin has no read route, so a WP draft created before 2026-08-12 may still name the act the old way.

**Not every act on the roster is a tribute act (client correction 2026-08-03).** A draft read "the tribute act Priscilla Presley is exactly what your audience is thinking about". She is Priscilla Presley. The client: "She's not a tribute act. She's just an act." The same is true of **The Platters** (the continuing official organization, not a tribute to itself), **Tony Danza**, **Reza**, **Michael Griffin**, **Vitaly** and **Calpulli Mex Dance Co.** Calling one of them a tribute is a factual error about a real person, published under the agency's name.

`is_tribute_act(act, original_artist)` in `lp/ai.py` is the single test: an act is a tribute **only** when `artists.md` gives it an original artist who is somebody else. A blank mapping counts as "not a tribute", deliberately: the failure it prevents (calling a real artist a tribute) is worse than the one it allows (not mentioning that a tribute is a tribute). Currently 15 of 24 acts classify as tributes.

Wired into four places, since asserting it once was how the error got out:
- The `generate_posts()` prompt label is now `Act:`, not `Tribute Act:`.
- `act_kind_instruction` states plainly which one this act is, and for a non-tribute forbids "tribute act", "tribute band", "tribute show", "pays tribute to", "channels" and "recreates".
- `generate_article()` says "a Love Productions act" instead of "Love Productions' tribute act", with the same prohibition.
- **`build_hashtags()` substitutes `#TributeBand` → `#LiveEntertainment`** for non-tribute acts. A `#TributeBand` tag on Priscilla Presley is the same error as the copy saying it, just harder to spot, and it was the engine's own doing rather than the model's.

**`find_act_video()` now requires the video title to name the act.** The Vimeo `query` parameter is a full-text search over titles, descriptions and tags, and the code took the top usable hit without ever checking it was the right act. Searching "Platters" on 2026-08-03 returned "Phil Dirt and the Dozers" and a package-show sizzle reel alongside the act's own promos, and the sort (promo first, then shortest) picked **"THE GOLDEN ERA OF ROCK & ROLL 2025 Sizzle"** over "The Platters 2026 Promo Video". The client spotted it: the footage was not the current line-up. Now `_names_act()` requires a majority of the act's name tokens in the title and returns **None** when nothing matches, because no clip beats another act's clip going out under this act's name. `_title_year()` also sorts the newest promo first, since an act re-shoots when the line-up changes, which is exactly the signal that was missed.

**Show, do not tell: cut the sentence that states the obvious (client direction 2026-08-03).** This extends the "never explain the buyer's business" rule to **every platform and every audience**. Client, verbatim: "We need to get rid of some of the fluff. And we should never be explaining talent buyers' jobs to them. We don't have to say the obvious, like: 'Her name isn't going anywhere,' or 'getting booked twice means the act is great,' etc. They know these things. Let's show, not tell."

The test in code and in the graph: **delete the sentence; if the reader loses no information, it was fluff.** That catches "the name still draws", "that says everything", "that's the whole story", "if your crowd knows the difference, this is the one", and any assertion that the act is great, special, or worth booking. Note the client's rewrite is **not shorter** than what it replaced: cutting fluff means cutting the *interpretation*, not the detail, and their version carries more fact ("the follow-up to her original, covering her life, her losses, and what came after"). Landed as a SHOW, DO NOT TELL block in the `generate_posts()` prompt, a third worked example in `voice/reference-posts.md`, and a second family in `humanizer.md`'s "explanatory kicker" section. Verified by regenerating the same topic: Facebook came back essentially identical to the client's own rewrite.

**Facebook now ends with a fixed booking line**, `Booking inquiries: info@loveproductions.com`, after the source link, taken from that rewrite. Note this is the **email**, not `STEVE_CALENDAR_LINK`: LinkedIn uses the calendar (buyers), Instagram uses a DM (no linkifying), Facebook uses the email because that is what the client wrote. All three are now deterministic instructions in `generate_posts()` rather than left to the model.

**Editing a post that is already queued to send: `edit_post_draft(..., keep_scheduled=True)`.** The only case where `saveToDraft` is False, so it *requires* an explicit **future** `scheduled_at` and raises without one. That guard is the lesson of the incident above: the damage came from an edit with neither `saveToDraft` nor a `dueAt`, which re-slotted the post into a past automatic slot and published it immediately. An explicit future `customScheduled` time cannot do that. Verified 2026-08-03 on a live scheduled post: status stayed `scheduled`, `dueAt` unchanged.

## LinkedIn analytics (self-learning)

LinkedIn API access was applied for but not approved. Instead, export analytics manually:

1. Go to the LinkedIn Company Page admin → **Analytics → Updates**
2. Click **Export** (top right) to download a CSV
3. Set `LINKEDIN_ANALYTICS_CSV=/path/to/export.csv` in `.env`
4. Run `python main.py --test-analytics` to confirm LinkedIn posts appear in the output

`lp/linkedin.py` parses the CSV and feeds the top performers into `fetch_top_performers()` alongside Meta posts. Re-export monthly (or whenever) to refresh the data. The CSV column names LinkedIn uses are: `Post title`, `Impressions`, `Likes`, `Comments`, `Shares`.

## Adding or editing artists

Edit `content-skill-graph/engine/artists.md`. The table maps `Tribute Act | Original Artist`. Leave Original Artist blank if not applicable. Changes take effect on the next run, no code change needed.

## Extending the skill graph

Drop a new `.md` file anywhere under `content-skill-graph/`. It gets picked up automatically by `load_skill_graph()` (alphabetical sort). Use the existing files as style reference, keep them instructional, not descriptive.

## Formatting

When editing the markdown docs, or writing anything client-facing, ***please*** don't use any em dashes at all. Always consider a full stop, new sentence, semi-colon, whatever works. Anything but em dashes. And please try to make what you write as succinct as possible, while still being effective. Do your best to keep things short.
